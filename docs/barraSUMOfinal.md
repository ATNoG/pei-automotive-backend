# SUMO Traffic Simulation — Ponte da Barra

## What this is

`scripts/utils/barraSUMOfinal/` contains a complete [Eclipse SUMO](https://sumo.dlr.de/) traffic simulation of the **Ponte da Barra** area in Aveiro, Portugal. It was designed to replace the hand-scripted, 2–6-car pytest scenarios with a realistic, continuous traffic stream at scale (~1 000 vehicles/hour, mixed types).

The road network was exported from OpenStreetMap via `osmWebWizard.py` and covers roughly:

```
SW corner: 40.6232°N, -8.7489°W
NE corner: 40.6382°N, -8.7234°W
```

## bridge.py — backend integration

`bridge.py` is the production integration. It runs SUMO headlessly via TraCI and at every simulation step PUTs every vehicle's GPS coordinates **directly to Eclipse Ditto** via HTTP — bypassing Hono/MQTT entirely.

### Why bypass Hono?

| Path | Cost per update |
|---|---|
| `send_position.py` (existing) | subprocess spawn + Python import + Hono TLS handshake + publish + Ditto readback ≈ **2–4 s** |
| `bridge.py` (direct Ditto REST) | one HTTP PUT on a keep-alive session ≈ **50–600 ms** |

`position_processor` subscribes to Ditto's WebSocket filtered on `exists(features/gps)`. A REST PUT to `/api/2/things/{id}/features` fires that event regardless of whether the update came through Hono or directly — the downstream pipeline is identical.

### One-time setup

```bash
cd scripts/utils/barraSUMOfinal
python3 -m venv .venv
.venv/bin/pip install eclipse-sumo traci sumolib requests python-dotenv
```

The backend `.env` must be present at the repo root (`pei-automotive-backend/.env`).

### Running

```bash
# Minimal demo (30 vehicles, 2 min, clean up on exit):
.venv/bin/python bridge.py \
    --max-steps 120 \
    --max-vehicles 30 \
    --real-time \
    --workers 24 \
    --cleanup

# Full 1-hour simulation, no vehicle cap:
.venv/bin/python bridge.py --real-time --workers 32 --cleanup

# With SUMO GUI (visualise the map):
.venv/bin/python bridge.py --gui --max-steps 120 --max-vehicles 30 --real-time --cleanup
```

### CLI flags

| Flag | Default | Description |
|---|---|---|
| `--workers N` | 16 | HTTP thread pool size |
| `--step-length S` | 1.0 | Simulation step in seconds |
| `--end-time T` | 3600 | SUMO end time (from `osm.sumocfg`) |
| `--max-steps N` | — | Stop after N sim steps (safety net) |
| `--max-vehicles N` | — | Publish at most N vehicles per step |
| `--metrics-interval S` | 2.0 | Seconds between metrics log lines |
| `--real-time` | off | Pace sim to wall-clock (prevents Ditto flood) |
| `--gui` | off | Launch `sumo-gui` instead of headless `sumo` |
| `--cleanup` | off | DELETE all simulated Ditto things on exit |

### Metrics output

```
[step=S sim=Ts active=N seen=M cap_skip=K | sent=X ok=X fail=E avg=Xms p50=Xms p95=Xms]
```

| Field | Meaning |
|---|---|
| `active` | Vehicles on road this step |
| `seen` | Total unique vehicles entered since start |
| `cap_skip` | Vehicles dropped due to `--max-vehicles` cap |
| `sent/ok/fail` | Ditto HTTP PUT results in this interval |
| `avg/p50/p95` | PUT round-trip latency (ms) |

## How vehicles map to Ditto things

Each SUMO vehicle `vid` (e.g. `"0"`, `"17"`) becomes:

- **Thing ID**: `org.acme:sumo-{slugified vid}` → e.g. `org.acme:sumo-0`
- **Policy**: shared `org.acme:sumo-sim-policy` (created once on startup)
- **Features**: `{"gps": {"properties": {"latitude": …, "longitude": …}}, "info": {"properties": {"emergency": false}}}`

Vehicle types containing "emergency" in their SUMO type ID are flagged `emergency: true` — the current `vehicledist.rou.xml` has no such type.

## What the detectors see

From the 120-step, 34-vehicle test run:

| Detector | Alerts fired |
|---|---|
| `speed_detector` | **1 222** — SUMO cars commonly exceed 80 km/h in 80 km/h zones |
| `overtaking_detector` | **51** — natural lane-change proximity events |
| `accident_detector` | Multiple — sumo-7 decelerated to near-zero; cars behind it were alerted directionally |
| `highway_entry_detector` | Multiple — ramp-to-mainline merge safety events |
| `traffic_jam_detector` | None yet — needs higher density or longer run to form queue |

Measured Ditto REST latency over VPN to the remote K3s cluster:

| Vehicles active | avg PUT | p95 PUT |
|---|---|---|
| ~1 | 224 ms | 392 ms |
| ~12 | 339 ms | 517 ms |
| ~23 | 625 ms | 748 ms |

Latency grows because Ditto/MongoDB indexes more things. Use `--cleanup` to keep the thing count low between runs.

## Known limitations

1. **No emergency vehicle type in `vehicledist.rou.xml`** — `emergency_vehicle_detector` won't fire from SUMO traffic. Add a `vType` with `"emergency"` in its ID to `vehicledist.rou.xml` and regenerate routes to test it.
2. **Ditto latency degrades with thing count** — always run with `--cleanup` or delete things manually between sessions.
3. **Traffic jam needs higher density** — at 1 000 veh/h on a small network with no signals or blockages, congestion doesn't organically form within 120 steps. Run the full 3 600 s or add a stopped vehicle to trigger a queue.
4. **SUMO vehicle IDs are numbers** — slugified to `sumo-0`, `sumo-1`, …, `sumo-999`. If you change `bridge.py`'s naming scheme, update `AppConfig.SUMO_USER_CAR_ID` in the frontend.
